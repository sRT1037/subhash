How LLMs Could Reshape Software Development

There's a real software explosion happening right now — you can see it everywhere. It's part of why GitHub's own infrastructure couldn't handle the traffic in one of its data centers recently, which knocked Git access out for several hours.

The bottleneck isn't code generation anymore

LLMs can now generate code at something like 20× the rate humans wrote it five years ago. But the actual bandwidth constraint during all this acceleration has shifted — it's not generation anymore, it's the human side of the loop: review. Even with code arriving this fast, someone still has to read and approve it before it ships.

Review speed is a trained skill, not a fixed one

People who've been in the industry for the past five years are already good at parsing and reviewing code in a fraction of a second — their brains were shaped by years of exposure to doing exactly that, well before LLMs existed. That's an advantage for them: they can review at speed even as generation accelerates. People who joined more recently don't have that same trained reflex yet, so they're effectively being asked to review code at 20× (maybe more) the rate anyone reviewed it at before LLMs — a much steeper ask. The upside is that once they build that same familiarity, they can keep pace with the flow too; it's a skill that compounds with exposure, not something you either have or don't.

Reviewing code visually instead of as text

One way to close that gap: stop reviewing purely as text, and review more visually instead — the way tools like DeepWiki or Gitingest already let you look at a codebase structurally rather than line by line. Human brains are more perceptive to images than to words — it's part of why you can still recall a visual memory from years ago far more easily than something you read as plain text. If review shifted toward that same visual, structural mode, it could absorb a meaningful chunk of the bottleneck that pure text review can't keep up with.

A general protocol for accelerating any kind of work

More generally, I think almost any work can be accelerated by being explicit about four things: what you're doing, why you're doing it, how you're doing it, and — if the work is output-based — what the expected output or outcome actually is. Naming all four up front, instead of only the first one or two, is what actually makes the acceleration real rather than just faster motion.

Self-questioning agents, and where hallucination actually comes from

Take that same protocol and point it at the agent itself, and you get something more interesting: a self-improving agent that can recognize what it's doing, why it's doing it, and how — the same four questions applied reflexively. Agents built that way should accelerate work further, and I think hallucination would drop as a side effect. Reducing hallucination doesn't necessarily require touching the model's architecture at all — you can get a lot of the way there by making the agent harness itself question and verify its own actions, checking whether what it just did was actually correct. That's basically giving the agent something like the self-monitoring loop humans run constantly — a rough analogue of consciousness, applied to a harness instead of a brain.
